# Goal：DeepSeek-V4.1-Flash 在 RTX 6000D 上的 P-only / D-only 逐内核优化

2026-11-17 立项。执行者：Claude（主会话负责引擎级实验和验收，子任务负责逐内核分析与优化）。

## 目标

在两台 8×RTX 6000D 节点上，把 DeepSeek-V4.1-Flash 的 **D-only** 和 **P-only** 金标准成绩尽可能提高。
做法分三步：先在各环节择优定出新基线，再逐内核算 SOL 找差距，最后按差距从大到小逐个优化。

成绩只认金标准，口径不变：

| 项目 | 金标准 | 现有成绩（11-16 复现值） |
| --- | --- | --- |
| D-only | DEP16、DSpark T=5、强制接受长度 5.35、输入 128928 / 输出 2048、C176 共同 decode 窗口；平均 TPOT < 10 ms 前提下的每卡输出吞吐 | 1108.58 tok/s/GPU，TPOT 9.901 ms（1102.62，9.951 ms） |
| P-only QCP8 | 单机 8 卡 QCP8/EP8、名义 94% 命中（缓存 121088）、C192、三个连续稳态窗口 | 4.632 req/s（4.596） |
| P-only ADP8 | 单机 8 卡 ADP8/EP8，其余同上 | 5.695 req/s（5.708） |

## 阶段

### 阶段 1：择优录用，定出基线 B1

对每个环节，在“现有实现”和“可拿到的备选实现”之间实测择优。备选来源：对方配置文档点名的库
（FlashInfer SM120 稀疏 MLA、DeepGEMM、DeepSelect）、节点上同事的移植补丁、
以及我们自己已有但没开的开关。已排定的候选：

1. Prefill MegaMoE 同机传输：`lsa_where_reachable` 对 `all_gin`。
2. Decode 注意力：FlashInfer SM120 稀疏 MLA 对现有 Triton `_selected_attention_*`。
3. Prefill 注意力：FlashInfer SM120 稀疏 MLA 对现有 gather + `_compact_attention`。
4. `wo_a`：cuBLAS BF16 对不改精度的替代，以及 MXFP8 量化版（改精度）。
5. 稠密 GEMM：DeepGEMM 对 FlashInfer b12x。
6. Prefill 的 NCCL 传输设置。

每个候选先做内核级正确性和微基准，胜出的并入实验树。全部并入后各跑一次金标准，得到 B1。

### 阶段 2：逐内核 SOL

对 B1 的 timeline 里占比不低于 1% 的每个内核（以及 GPU 空闲和启动开销），给出：

- 工况：每次启动的行数、形状、每步或每批的启动次数。
- 三个下限：算力（FLOPs ÷ 实测可达的张量核峰值）、显存带宽（必须读写的字节 ÷ 实测带宽）、
  跨卡链路（必须传输的字节 ÷ 实测链路带宽）。峰值和带宽在本机实测标定，不用估算值。
- SOL = 三者最大值；达成率 = SOL ÷ 实测；差距 = 实测 − SOL，折成每步或每批的毫秒。
- 瓶颈类型和差距的构成（固定开销、访存、调度、通信等待等）。

每条 SOL 结论要经过独立复核，复核者的任务是找错。

### 阶段 3：逐内核优化

按“差距 × 可行性”排序，逐个处理。每一项的流程：

1. 写清假设：差距来自哪里，改什么，预期省多少。
2. 在实验树里改，不动冻结目录。
3. 内核级验证：与现有实现逐元素比较（等价版要求在该内核现有测试容差内），再在真实工况形状上测前后耗时。
4. 通过后并入，累计若干项后跑金标准；金标准不过或变慢就回退并记录原因。

### 阶段 4：验收和交付

- 最终的 D-only、P-only（QCP8 和 ADP8）金标准各跑一次，核对有效性（窗口、请求数、JIT、接受率）。
- 更新后的 timeline 占比表和 SOL 表。
- 代码以“基线提交上的未提交改动”形式交付到 `tokenspeed-vs-main` 检出，节点上的实验树与之逐文件一致。

## 约束

- **精度**（用户 11-17 决定）：允许改变数值精度的优化，但成绩分两份报告——“等价版”只含数值等价或落在
  现有测试容差内的改动，“改精度版”在其上叠加改精度的改动。两份都要跑金标准。改精度版不做模型质量结论。
- **节点**：1P1D 服务经用户同意停掉，做完不重启（用户 11-17 决定）。不停别人的进程，不做全局
  `pkill python`，不清 `/dev/shm`，只结束确认属于本次实验的 PID。
- **目录**：不修改冻结目录（`serving-runtime-v3`、`serving-kernel-v20`）、`-megamoe` 实测目录、
  venv、交接包。所有改动在新的实验目录里，用它自己的环境脚本指过去。
- **测试**：不跑 smoke test；内核级验证之后直接跑金标准。强制接受长度 5.35 和 121088 前缀不变。
  P 的成绩不含 P→D 的 KV 传输。JIT 是否落入正式窗口需要人工核对。
- **记录**：不更新 `REPORTS.md`；不做 git 暂存、提交或推送；SSH 密码不写进任何文件。
- **GPU 使用**：引擎级运行独占所需的卡；单卡微基准各占固定的卡，互不重叠；两类不同时用同一张卡。

## 完成标准

满足以下全部条件才算完成：

1. B1 已定，且每个候选都有“采用 / 不采用”的实测依据。
2. 占比不低于 1% 的每个内核都有经过复核的 SOL、达成率和差距。
3. 差距排名靠前、合计覆盖 Decode 每步和 Prefill 每批至少 80% 差距的内核，逐个有结论：
   已优化并量出收益，或者说明为什么做不了（并附试过的方案和数据）。
4. 最终金标准成绩有效，等价版和改精度版各一份，并与现有成绩并排列出。

- 失败的尝试、回退的改动、没来得及做的项，都要列出来。
- 微基准的收益不等于金标准的收益，以金标准为准。
