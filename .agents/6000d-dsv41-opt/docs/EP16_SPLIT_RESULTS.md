# 两节点（EP16）上的 split MegaMoE：两分布调优、打包分发、按行数分桶和端到端结果

日期 2026-11-26。两台 8x RTX 6000D（156 SM），attention DP16、MoE EP16，开关集 `d7-same.sh`。
`mega_moe` 指 FlashInfer 的常驻融合 kernel，`mega_moe_split` 指 CuTe DSL 的分离式 kernel（目标模型用它，
DSpark 草稿模型留在常驻 kernel 上）。两个后端跑的是同一份 FlashInfer 源码：`flashinfer/README.md` 里的提交加补丁。

原始数据在 `results/ep16-split-20261126/`，脚本在 `tuning/`、`realtext/`、`launch/`，放置求解在 `placement/`。

## 结论

1. **按两个路由分布调优，调不出比现有表更好的配置。** 规则是：默认配置做初始基线；候选在 balanced 或
   power-law 任一分布上比当前基线慢 0.5% 以上就排除，否则两个耗时取平均，更低就替换基线。128 行和 96 行两档
   都停在表里 128 行档原有的那组配置上。
2. **split 输给常驻 kernel 的原因是路由偏斜，不是调优。** balanced 路由下 split 到每 rank 144 行都更快；
   power-law 路由下从 32 行起就更慢（32 / 64 / 96 / 128 行慢 11% / 22% / 10% / 14%），而且在旋钮空间里没有
   配置能把这个差距补上。真实流量落在两者之间。
3. **打包分发（pack）是 EP16 上最大的一项收益。** 这段发送端代码原先只在 kernel 作者的独立 runner 里，
   这里移植进了 FlashInfer。64 行一档每次 launch 从 768.5 降到 658.9 微秒；真实文本端到端在每 GPU
   4 / 8 / 16 / 24 路多出 6.9% / 11.3% / 17.9% / 19.5% 的吞吐。
4. **按 DSpark 的行数加编译桶（每请求 6 行，6×2^N 行）收益小，而且不是每档都有。** balanced 路由下 kernel 级
   快 0.3% 到 5.9%，前提是同时把 pack 的行数门槛降下来（否则 24 行的桶反而慢 7%）。放进引擎后，1、2 路
   有收益（真实文本吞吐 +1.2% / +3.0%，步时测量步时 -1.8% / -4.0%），其余不变；96 行的桶在 16 路是
   负收益（真实文本吞吐 -2.7%，步时测量只重排的放置下 +2.1%，副本放置下没有差别），不建议加。
5. **端到端要按负载选后端。** 真实文本加静态放置：每 GPU 8 路及以下 split 快 5.6% 到 16.6%，12 路打平，
   16 路起常驻 kernel 快。合成 token 的步时测量（第 5 节的六组对照，放置用留出样本求解）：不做放置时
   split 在 1、2 路短 15% / 9%，4 路打平，8 路起常驻 kernel 快；只重排时 1 到 4 路 split 短 10% 到 17%，
   8 路起常驻 kernel 快；每 rank 加 4 个副本后 split 领先到 8 路（短 3% 到 18%），16 路起常驻 kernel 快。

## 1. kernel 级：路由分布决定谁更快

一次 MoE launch 的耗时（微秒），EP16，16 个 rank 里最慢的那个，100 次 launch 的中位数，每次之前冲掉 L2。
power-law 是 runner 的 Zipf 路由（指数 1.0，热点专家随机落在某些 rank 上，不做任何放置）。常驻 kernel 只算
路由专家（不含共享专家），用引擎里的 `all_gin` 传输。

| 每 rank 行数 | 16 | 32 | 64 | 96 | 128 | 256 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 常驻 kernel，balanced | 704.5 | 735.2 | 827.4 | 888.8 | 915.5 | 1183.7 |
| split 调优表加打包，balanced | 554.1 | 558.0 | 658.9 | 754.5 | 875.0 | 1435.0 |
| split 对常驻，balanced | -21.3% | -24.1% | -20.4% | -15.1% | -4.4% | +21.2% |
| 常驻 kernel，power-law | 682.0 | 749.5 | 876.5 | 1038.3 | 1175.6 | 1720.3 |
| split 最好的配置，power-law | 570.3 | 835.5 | 1067.8 | 1143.4 | 1344.9 | 约 2980 |
| split 对常驻，power-law | -16.4% | +11.5% | +21.8% | +10.1% | +14.4% | 约 +73% |

- balanced 两行都是经 TokenSpeed 的封装量的（96 行跑在自己的 96 行桶里，见第 3 节）。split 的 power-law 是
  kernel 作者独立 runner 的读数：96、128 行是两分布规则选出的配置（3 次试验的中位数），16 / 32 / 64 行取
  现有表和通用预设里快的那个（单次试验），256 行是现有表的配置（三次 2984 / 2978 / 2943）。常驻 kernel 的
  power-law 用同一个生成器和种子的路由。两条测量路径在同一配置上相差不到 1.5%。
- 常驻 kernel 换一个路由种子（6197）在 power-law 下是 673.8 / 727.0 / 886.8 / 1040.4 / 1214.5 / 1746.9，同一种子
  重复三次相差不到 0.3%。
- 128 行那一档对规则“放行”之外的候选也测了 power-law（balanced 比最优慢 12% 以内的 23 组）：全部落在 1315
  到 1460 微秒之间。也就是说，即使完全不顾 balanced，split 在 128 行的 power-law 上最好也只有 1315，
  仍比常驻 kernel 慢 12%。
- split 对偏斜更敏感：128 行从 balanced 到 power-law，常驻 kernel 慢 28%，split 的规则默认配置慢 65%，
  调优后的配置慢 56%。

## 2. 两分布调优

工具是 `tuning/tune_two_routes.py`（`--rule sequential`），它驱动 kernel 作者的调优工具和独立 runner，
试验协议不变（整图 launch、冷 L2、20 次预热、100 次计时、取各 rank 最慢值的中位数）。

规则：

1. 规则默认配置（不带表、不带通用 decode 预设）是初始基线。
2. 每个候选跟**当前基线**比。balanced 或 power-law 任一分布慢 0.5% 以上，排除。否则两个耗时取平均，
   低于基线的平均就成为新基线。
3. 候选顺序：调优包的预设，调优包自带的起点，现有表各档的配置，然后围绕当前基线把每个旋钮扫一遍。
4. 最后用第二个路由种子把最终配置、默认配置和现有表的配置再量一遍。

power-law 的单次试验在大行数上不稳：256 行同一个配置三次是 2877 / 3033 / 3062 微秒（6.5%），远大于 0.5%
的门槛；96 行和 128 行三次相差不到 0.2%。所以 power-law 的耗时取 3 次试验的中位数（第一次就比基线慢出
`--pl_margin` 的候选直接排除）。balanced 的重复差在 0.1% 到 0.3%。

结果（微秒；括号里是对规则默认）：

| 档位 | 规则默认 balanced / power-law | 最终配置 balanced / power-law | 最终配置是什么 |
| --- | --- | --- | --- |
| 128 行 | 1017.3 / 1681.0 | 863.6 (-15.1%) / 1344.9 (-20.0%) | 现有表 128 行档的配置；最后一步的变化是 +0.02% / -0.1% |
| 96 行 | 904.7 / 1291.7 | 763.6 (-15.6%) / 1143.4 (-11.5%) | 同一组配置；最后一步的变化是 -0.03% / -0.03% |

- 96 行一共考虑了 36 个候选：26 个因某一分布慢 0.5% 以上被排除，6 个平均不更快，4 个成为过基线
  （通用预设、现有表 32 行档、现有表 128 行档、把 K2 warp 数显式写成 8）。
- 第二个种子上，balanced 的收益不变（128 行 -15.1%，96 行 -15.2%），power-law 的收益几乎消失
  （-0.3%，-0.4%）：规则默认配置在第一个种子的 power-law 路由上特别慢，换种子后和调优配置一样快。
  power-law 上的收益取决于热点专家落在哪些 rank，不要把 -20% 当成稳定收益。
- 256 行：单次试验里现有表的配置在 power-law 上比默认慢 3.7%，重复后变成快约 3%。这一档的差别在
  噪声之内，表里保持原配置。
- 192、48、24、12、6 行还没有按这个规则调；这几个桶目前用表里最近一档的配置。

规则在这一轮里有过两个更早的读法（起点取“两分布平均最好的合格起点”，之后跟当前最优比，或者只跟规则
默认比；平均改善超过 0.5% 才接受）。128 行和 256 行在这两种读法下的结果也在结果目录里：128 行同样是
现有配置。

表的变化：`mega_moe_sm120_split_tuned.json` 多了一个 96 行档，并为每 rank 4 个副本槽的放置（448 个专家槽）登记了同一张表。96 行档只有在 FlashInfer 编译了
96 行的桶时才会被用到（见下一节），默认的桶下 96 行跑 128 行的桶和 128 行档。

## 3. FlashInfer 侧的两处改动

补丁和说明在 `flashinfer/`。

**打包分发。** split kernel 通过 RDMA 把行发给别的 NUMA 节点和另一台主机上的专家。不打包时每个目标收到整段
输入，打包后只收到路由给它的行加一张行映射。kernel 作者的独立 runner 在 EP16 上从每 rank 32 行起默认打包，
FlashInfer 的适配层没有发送端，所以引擎里一直没有打包。移植之后（balanced 路由，微秒）：

| 行桶 | 7 | 16 | 32 | 64 | 128 | 168 | 256 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 规则默认，不打包 | 609.7 | 658.9 | 750.4 | 903.6 | 1261.2 | 1456.5 | 2049.8 |
| 调优表，不打包 | 521.8 | 552.1 | 611.2 | 768.5 | 1105.9 | 1298.9 | 1880.3 |
| 规则默认，打包 | 610.8 | 658.3 | 695.6 | 792.8 | 1027.0 | 1157.9 | 1598.9 |
| 调优表，打包 | 517.6 | 554.1 | 558.0 | 658.9 | 875.0 | 997.7 | 1435.0 |
| 常驻 kernel | 677.9 | 704.5 | 735.2 | 827.4 | 915.5 | 1009.7 | 1183.7 |

现有的表是在不打包的条件下调的。作者的 tuner 在打包条件下重新调，16、64、128、256 行选出的是同一组旋钮，
32 行不同但表里那组快 0.7%，所以表不需要因为打包而改。输出的参考校验在打包前后误差相同。

**按行数加编译桶。** split kernel 按行桶编译，一次调用用能装下它的最小桶。默认的桶是 7、16、32、64、128、
168、256……。DSpark 块长 5 时每个请求 6 行，每 GPU 1 / 2 / 4 / 8 / 16 / 32 路是 6 / 12 / 24 / 48 / 96 / 192 行，
落在 7 / 16 / 32 / 64 / 128 / 256 的桶里。加上 6×2^N 的桶之后每个并发档跑的就是按它的行数编译的 kernel
（balanced 路由，微秒，调优表）：

| 每 rank 行数 | 6 | 12 | 24 | 48 | 96 | 192 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 默认的桶 | 505.3 | 552.4 | 536.0 | 609.7 | 780.3 | 1243.6 |
| 加桶，打包门槛不变（32 行） | 503.3 | 538.1 | 574.9 | 607.7 | 754.5 | 1232.5 |
| 加桶，所有桶都打包 | 498.6 | 519.6 | 533.4 | 607.7 | 754.5 | 1232.5 |
| 变化 | -1.3% | -5.9% | -0.5% | -0.3% | -3.3% | -0.9% |

24 行的桶低于默认的打包门槛，单独加桶会比原来慢 7%；把门槛降到 6 行后，6、12、24 行都比不打包快。
两节点 16 个 rank 的 kernel 测试在加桶后通过（27 项通过，5 项跳过），每个计时过的桶都过了输出的参考校验。

代价：引擎启动时每个桶都要编译和预热一遍。带这六个桶（共 18 个桶）的 split 引擎（步时测量的启动参数，
KV 池 524288）显存峰值 79.3 GB，再加每 rank 4 个副本槽是 82.4 GB（卡上共 85.65 GB）；开关集里去掉 96 行
之后（17 个桶）是 78.7 和 81.9 GB。放进引擎后的效果见第 4、5 节：不是每一档都变快。

## 4. 端到端：真实文本加静态放置

负载见 `realtext/README.md`：8192 token 的真实文本提示词，输出 1024 token，贪心，真实的 DSpark 接受率，
经 HTTP 网关的闭环波次，只量 decode 窗口。放置文件用另一套提示词（种子 43，和被测的一套没有重复）录的
负载画像求解，只重排、不加副本（记作 r0）。真实文本的路由不做放置时最忙的 rank 是平均的 1.99 倍，
重排后 1.01 倍。

整机每秒输出 token（16 张卡），取前三个分布均匀的有效波次的中位数：

| 每 GPU 路数 | 1 | 2 | 4 | 8 | 16 | 24 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 常驻 kernel | 1644 | 2864 | 5330 | 9456 | 16093 | 20963 |
| split：调优表，打包，默认的桶 | 1901 | 3338 | 6103 | 9990 | 15422 | 18899 |
| split 对常驻 | +15.6% | +16.6% | +14.5% | +5.6% | -4.2% | -9.8% |
| split：规则默认，打包 | 1766 | 3068 | 5508 | 9155 | 13902 | 16272 |
| split：调优表，不打包 | 1899 | 3336 | 5709 | 8978 | 13080 | 15818 |
| 常驻 kernel，每 rank 4 个副本的放置 | 1683 | 2906 | 5375 | 9583 | 16310 | 21417 |

- TPOT（毫秒）：常驻 kernel 9.73 / 11.17 / 12.01 / 13.54 / 15.91 / 18.32，split 8.42 / 9.59 / 10.49 / 12.81 /
  16.60 / 20.32。
- 调优表的收益（都打包）：7.7% / 8.8% / 10.8% / 9.1% / 10.9% / 16.1%。打包的收益（都用表）：0 / 0 / 6.9% /
  11.3% / 17.9% / 19.5%（1、2 路不到 32 行，本来就不打包）。少了任何一个，split 从 8 路起就落后于常驻 kernel。
- 接受长度 split 比常驻 kernel 低约 1%（16 路 3.296 对 3.333）：两个 kernel 的输出在同一精度档但不是逐位
  相同，这个差已经算在吞吐里。
- 交叉点在每 GPU 8 路和 16 路之间，比 balanced 路由下 kernel 级的预测（24 到 32 路）低。原因是第 1 节：
  真实路由即使做了重排，每层仍有专家独占超过半个 rank 的平均负载。另外 split 的共享专家不在 kernel 里
  融合，每步多 1 到 1.6 毫秒。
- 副本对常驻 kernel 的帮助在这个负载上很小（0.8% 到 2.4%），因为重排已经把负载摊平了。

用 6×2^N 的桶加全桶打包重测 split（同一个放置，另加每 GPU 12 路这一档；常驻 kernel 的 12 路是单独补的一次
运行）：

| 每 GPU 路数 | 1 | 2 | 4 | 8 | 12 | 16 | 24 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 常驻 kernel | 1644 | 2864 | 5330 | 9456 | 13099 | 16093 | 20963 |
| split，默认的桶 | 1901 | 3338 | 6103 | 9990 | — | 15422 | 18899 |
| split，6×2^N 的桶，全桶打包 | 1924 | 3437 | 6122 | 10032 | 约 13195 | 14998 | 18916 |
| 新桶对默认的桶 | +1.2% | +3.0% | +0.3% | +0.4% | — | -2.7% | +0.1% |
| 新桶的 split 对常驻 | +17.0% | +20.0% | +14.9% | +6.1% | +0.7% | -6.8% | -9.8% |

- 12 路这一档两个后端打平，交叉点就在这里。split 的 5 个波次里只有 2 个分布均匀（13194 和 13197），不足
  3 个，所以写“约”；常驻 kernel 是 3 个均匀波次的中位数。
- 新桶的收益在 1、2 路。16 路（96 行）慢 2.7%，和步时测量里只重排放置下的 +2.1% 方向一致：96 行的专用桶在 balanced
  路由下快 3.3%，在真实文本和合成 token 的路由下都更慢。并发在每 GPU 16 路附近时不要加这个桶，把 96 从
  `MEGAMOE_EXTRA_COMPILE_BUCKETS` 里去掉，96 行就回到 128 行的桶。
- 多 6 个桶的代价：引擎就绪 871 秒（默认的桶 691 秒），显存就绪时 75.2 GB、结束时 79.4 GB（默认的桶
  72.0 / 76.1 GB）。



## 5. 端到端：步时测量（合成 token）加静态放置

`launch/README.md` 里“Step-time measurements”那一套：131072 token 的上下文，每个 rank 固定 1 到 32 个
请求，每步保留全部 6 个验证 token（模拟接受长度 6；它只让每一步形态一致，不是真实接受率），量 rank 0 的
步间隔。合成 token 的路由比真实文本集中得多：不做放置时最忙的 rank 是平均的 2.87 倍，只重排降到 1.73 倍
（40 层里有 31 层单靠重排压不到算力配额以内），每个 rank 加 4 个副本槽降到 1.09 倍。

### 5.1 对照矩阵：两个后端 × 三种放置

六个引擎在同两台节点上连续跑完（约 2 小时），每组只改一个因素：

- 相同的：FlashInfer 源码（`flashinfer/README.md` 的提交加补丁）、本分支的代码（split 用仓库里的调优表）、
  `ts serve` 参数、`d7-same.sh`、输入（六组每个测点的输入哈希相同）。
- 不同的：后端；放置文件（不做、只重排、每 rank 4 个副本槽）；split 一侧另有
  `switch-sets/d7-same-split-ep16.sh` 的两个设置（桶 6、12、24、48、192 行，所有桶打包）。
- 放置用留出样本求解：画像是另一批输入录的（请求尾部用另一个随机种子，和被测输入只有共享前缀相同），
  被测的输入没有参与求解。

decode 每步耗时（毫秒）：

| 每 rank 请求数 | 1 | 2 | 4 | 8 | 16 | 32 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 常驻 kernel，不做放置 | 30.37 | 31.64 | 35.06 | 40.68 | 53.72 | 81.42 |
| 常驻 kernel，只重排 | 30.79 | 32.02 | 34.83 | 38.48 | 48.19 | 68.83 |
| 常驻 kernel，4 个副本 | 32.22 | 33.59 | 35.94 | 38.71 | 45.21 | 59.97 |
| split，不做放置 | 25.86 | 28.70 | 34.60 | 47.28 | 62.94 | 108.80 |
| split，只重排 | 25.52 | 27.10 | 31.21 | 39.94 | 53.72 | 90.19 |
| split，4 个副本 | 26.53 | 28.11 | 31.14 | 37.53 | 47.94 | 70.01 |

split 对常驻 kernel，同一种放置（负数是 split 的步时更短）：

| 每 rank 请求数 | 1 | 2 | 4 | 8 | 16 | 32 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 不做放置 | -14.9% | -9.3% | -1.3% | +16.2% | +17.2% | +33.6% |
| 只重排 | -17.1% | -15.4% | -10.4% | +3.8% | +11.5% | +31.0% |
| 4 个副本 | -17.7% | -16.3% | -13.4% | -3.0% | +6.0% | +16.7% |

- split 在小并发领先、常驻 kernel 在大并发领先，放置越均衡分界越靠后：不做放置时 4 路打平，只重排时
  分界在 4 路和 8 路之间，4 个副本时在 8 路和 16 路之间（和真实文本上的位置一致）。
- 放置对 split 的帮助比对常驻 kernel 大。相对不做放置，只重排：常驻 kernel
  +1.4% / +1.2% / -0.7% / -5.4% / -10.3% / -15.5%，split -1.3% / -5.6% / -9.8% / -15.5% / -14.6% / -17.1%；
  4 个副本：常驻 kernel +6.1% / +6.2% / +2.5% / -4.8% / -15.8% / -26.3%，split
  +2.6% / -2.1% / -10.0% / -20.6% / -23.8% / -35.7%。
- 副本在小并发是负收益：相对只重排，1、2 路两个后端都慢 4% 到 5%（1.0 到 1.6 毫秒）；split 从 8 路起、
  常驻 kernel 从 16 路起才变快（32 路：常驻 kernel 68.83 到 59.97，split 90.19 到 70.01）。小并发用只重排，
  大并发加副本。
- 每档取最快的一组：25.52（split，只重排）/ 27.10（split，只重排）/ 31.14（split，4 个副本）/
  37.53（split，4 个副本）/ 45.21（常驻，4 个副本）/ 59.97（常驻，4 个副本）毫秒。
- 重复性：每组的两个正式轮各自算均值，最多差 1.2%，多数在 0.5% 以内。
- 显存峰值（卡上 85.65 GB）：常驻 kernel 68.3 / 68.4 / 71.4 GB，split 78.7 / 78.7 / 81.9 GB
  （不做放置 / 只重排 / 4 个副本）。split 加 4 个副本后余量 3.8 GB。

## 6. 怎么用

- FlashInfer：`flashinfer/README.md` 的提交加补丁。
- 开关集：常驻 kernel 用 `switch-sets/d7-same.sh`；split 用 `switch-sets/d7-same-split-ep16.sh`
  （加桶，所有桶打包），启动时 `OPT_MOE_BACKEND=mega_moe_split`。开关集里的桶是 6、12、24、48、192 行，
  不含 96：6 和 12 行有收益，24、48、192 行持平，96 行在端到端上是负收益，去掉后 96 行跑默认的 128 行桶。
  第 5.1 节的对照矩阵是用这个列表跑的；真实文本（第 4 节）跑的是带 96 的六个桶。
- 放置：按自己的流量录画像、求解（`placement/README.md`），两个后端都设
  `TOKENSPEED_MOE_EXPERT_PLACEMENT`。
- 选后端：没有运行时自动切换，一个引擎只跑一种。按上面两节的交叉点和自己的并发来选，最好在自己的流量上
  两个都量一遍。

## 7. 范围和没做的

- 真实文本只有一套 ShareGPT 提示词（160 条里取）；放置的画像来自同类的另一套提示词。
- 两个后端的输出不是逐位相同，这里没有做任务级的质量回归。
- 192、48、24、12、6 行还没有按两分布规则调。
- 带副本的放置在 split 上需要表里有对应槽位数的条目（FlashInfer 按专家槽总数精确匹配表）；表里现在有 384 和 448 两个槽位数（448 只在步时测量上跑过引擎，旋钮没有针对它调），其他副本数要自己加一张表。
- 没有做运行时按行数在两个 kernel 之间切换。单节点上试过一个这样的构建，两节点上没有。
