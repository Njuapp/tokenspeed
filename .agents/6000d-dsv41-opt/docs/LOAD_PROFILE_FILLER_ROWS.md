# 负载统计把 CUDA 图回放的填充行算了进去：问题、修复和对结果的影响

日期 2026-11-27。涉及 `TOKENSPEED_MOE_LOAD_PROFILE`（`python/tokenspeed/runtime/moe/expert_file_placement.py`）
录的 decode 负载统计，以及用它求解的静态专家放置（`placement/`）。

原始数据在 `results/ep8-vs-ep16-20261127/`，检查工具在 `placement/`。

## 结论

1. **修复前，decode 负载统计把填充行也数了进去。** attention DP 下每个 rank 每一步都回放“最忙那个 rank 的
   批大小”对应的 CUDA 图，请求少的 rank 用填充行补齐，空闲的 rank 整批都是填充行；图的预热和捕获也带假行。
   统计对 `topk_ids` 的每一行都计数，没有区分。
2. **真实文本的两份统计里填充行占 30%（EP16）和 17%（EP8）。** 填充行的输入都一样，所以每层都落在固定的
   几个专家上，求解器把它们当成了热点。合成 token 的步时测量统计里只有 2% 到 4%，prefill 的统计不受影响
   （prefill 不走图回放）。
3. **用这样的统计解出的放置几乎没有均衡真实流量。** 按不含填充行的统计评估，最忙的 rank 除以平均值：

   | | 不做放置 | 旧放置，只重排 | 旧放置，带副本 | 新放置，只重排 | 新放置，带副本 |
   | --- | ---: | ---: | ---: | ---: | ---: |
   | EP16 | 1.60 | 1.45 | 1.24 | 1.00 | 1.00 |
   | EP8 | 1.30 | 1.21 | 1.19 | 1.00 | 1.00 |

4. **已修复**（提交 `fix(moe): the expert load profile counts real rows only`）：前向在每次 decode 图回放前告诉
   统计“这次回放里有几个请求是真的”，计数时每一行乘 1 或 0。`TOKENSPEED_MOE_LOAD_PROFILE_LIVE_ROWS=0` 恢复旧计数。
   引擎里验证过：统计到的 decode 周期数与请求日志里真实请求的周期数之比，EP16 和 EP8 都是 1.004（旧计数是
   1.43 和 1.21）。
5. **对吞吐的影响**（真实文本，同一晚、同一棵代码树，只换放置文件）：EP16 的 split 带 4 个副本槽时每 GPU 1 到 4 路不变，
   8 / 12 / 16 / 24 路多 3.2% / 4.3% / 5.4% / 8.0%；只重排时每档多 3.9% 到 9.4%；EP8 的 split 多 0.1% 到 1.4%
   （EP8 的流量本来就更均匀）。
6. **受影响的已发布数字**：`docs/EP16_SPLIT_RESULTS.md` 第 4 节和 `launch/README.md` 里 2026-11-26 的真实文本
   结果。它们是有效的实测（取数窗口里各 rank 是满的，没有填充行），但所用的放置文件不是按真实流量解的；
   “不做放置时最忙的 rank 是平均的 1.99 倍，重排后 1.01 倍”和“副本只多 0.8% 到 2.4%”说的是含填充行的统计。
   用新放置重测的结果在 `docs/EP8_VS_EP16.md` 和本文第 6 节。合成 token 步时测量的结论不变。

## 1. 填充行从哪来

- attention DP 下各 rank 各自持有请求，但每一步所有 rank 回放同一个尺寸的 decode 图：`forward_step.py` 取各
  rank 批大小的最大值，向上取到最近的捕获尺寸。
- 某个 rank 的真实请求数少于这个尺寸时，多出来的位置填占位请求（序列长度 1，用哨兵槽位）；没有请求的
  rank 回放的整批都是占位请求。占位请求照常走完每一层，包括 MoE 的路由和专家计算。
- 每个捕获尺寸在捕获前还有 4 次预热前向，输入也是假行。
- 不走图的前向（prefill 的 extend）从不补齐，所以 prefill 的统计没有这个问题。
- 上游自己的在线 EPLB 计数器有行掩码（`runtime/moe/expert_load_rows.py`），但只在开在线 EPLB 时才建；
  我们这个离线统计没有用它。

填充行的输入完全相同，所以在前几层它们全部选中同样的 top-k 专家（第 0 层：33、16、360、117、79、247；
第 1 层：247、41、326、66、290、233），深层有少数几种变体。

## 2. 有多少

用两种互相独立的办法数：

- **按请求日志**：引擎日志里每个请求结束时有一行 `Req: <id> Finish! Accept_num_tokens_avg: <a>`，输出 N 个
  token 的请求跑了 (N - 1) / a 个 decode 周期，每个周期在目标模型里是 6 行。把统计文件写入时刻之前结束的请求
  加起来，就是“应该数到的周期数”。
- **按填充专家**：第 0、1 层那六个固定专家里计数最小的一个，是填充行数的下界。

| 统计 | 负载 | 数到的周期 ÷ 真实请求的周期 | 填充行占比 |
| --- | --- | ---: | ---: |
| EP16 真实文本，11-26（旧计数） | 留出提示库，每波 160 路 | 1.43 | 30.0%（各 rank 21% 到 42%） |
| EP8 真实文本，11-27（旧计数） | 同上，每波 80 路 | 1.21 | 17.2% |
| EP16 真实文本，11-27（新计数） | 同上 | 1.004 | 0.3% |
| EP8 真实文本，11-27（新计数） | 同上 | 1.004 | 0.3% |
| EP16 步时测量，合成 token（旧计数） | 每 rank 固定 1 到 32 个请求 | — | 不超过 2.0% |
| EP8 步时测量，合成 token（旧计数） | 同上 | — | 不超过 3.1% |
| EP8 decode 金标准，合成 token（旧计数） | 金标准的并发 | — | 不超过 4.0% |

真实文本的统计填充行多，是因为闭环分波的负载里各 rank 的请求不同时到、不同时结束：一波的头尾各 rank 的
路数不一样，少的 rank 一直在补齐；波与波之间还有 rank 完全空闲却跟着回放。步时测量每个 rank 的请求数固定
且相同，只有预热和捕获带假行。

## 3. 旧放置在真实流量上的均衡程度

`placement/eval_placement.py` 把一个放置文件套在一份统计上，算每层各 rank 的负载。下表全部用不含填充行的
新统计评估（40 层的平均；括号里是最差的一层）：

| 放置 | 最忙的 rank ÷ 平均 | 跨 rank 的路由占比 |
| --- | ---: | ---: |
| EP16，不做放置 | 1.601 (2.139) | 93.8% |
| EP16，旧，只重排 | 1.447 (1.469) | 93.8% |
| EP16，旧，4 个副本槽 | 1.240 (1.299) | 92.7% |
| EP16，新，只重排 | 1.003 (1.099) | 93.8% |
| EP16，新，4 个副本槽 | 1.000 (1.000) | 85.7% |
| EP8，不做放置 | 1.302 (1.664) | 87.5% |
| EP8，旧，只重排 | 1.205 (1.219) | 87.5% |
| EP8，旧，3 个副本槽 | 1.185 (1.219) | 84.9% |
| EP8，新，只重排 | 1.000 (1.000) | 87.5% |
| EP8，新，3 个副本槽 | 1.000 (1.000) | 84.3% |

- 旧放置把填充专家当成最热的专家去摊，真实流量里的不均衡大部分没动。
- 旧的副本也大多给了填充专家：EP16 旧放置的副本只把跨 rank 路由从 93.8% 降到 92.7%，新放置降到 85.7%。
- EP8 的放置请求的是每 rank 8 个副本槽，求解器只用了 3 个（共 408 个专家槽）：它只复制负载超过平均 rank
  负载 25% 的专家，EP8 的 rank 平均负载是 EP16 的两倍，够得上的专家更少。EP16 请求 4 个就用满 4 个
  （448 槽），请求 8 个会用到 7 个（496 槽）。

## 4. 修复

- `ExpertLoadProfile.mark_live_requests(live, replayed)`：前向在每次 decode 图回放前调用，说明这次回放的
  `replayed` 个请求里前 `live` 个是这个 rank 的真实请求；预热、捕获和空闲回放是 0。回放后恢复成“全部算”。
- 计数时第 i 行（共 R 行）算数的条件是 `i * replayed < live * R`，即每个请求的行数相同、真实请求排在前面。
  这个判断是图里的张量运算，标记值放在设备上的一个小张量里，回放前原地改写，所以不需要重新捕获图。
- 不走图的前向不调用标记，每一行都算。
- `TOKENSPEED_MOE_LOAD_PROFILE_LIVE_ROWS=0` 恢复旧计数；统计文件的 `coverage.live_rows_only` 记录用的是哪种。
- 单元测试：`test/runtime/moe/test_expert_load_profile.py`。

## 5. 引擎里的验证

新代码重录两份真实文本统计（EP16 和 EP8，留出提示库），然后：

- `placement/check_live_rows.py 统计目录 引擎日志..`：数到的周期数 ÷ 真实请求的周期数，两份都是 1.004。
- 填充专家的下界：0.3%（旧计数同一晚在 EP8 上是 17.2%）。
- 各 rank 的统计文件不是同时写的（只有不走图的前向才写文件），最多能差一波。检查时要按每个 rank 自己的
  写入时刻去对请求日志，否则会误判；`check_live_rows.py` 是这么做的。

## 7. 怎么检查自己的统计

求解之前先跑 `placement/check_live_rows.py`（需要引擎日志），或者看 `coverage.live_rows_only` 是否为 true。
已有的旧统计不能事后修正：从每层减去“填充专家”的计数只能得到下界，深层的填充行有多种落点，也有本来就热的
专家，减不干净。重录。

## 8. 没做的

- 填充行本身要不要花 MoE kernel 的时间，没有量。它们在 kernel 收到的批里，各 rank 负载不齐时（真实业务的
  常态）也许值得单独处理。
- 在线 EPLB 路径（上游的计数器）没有动，它有自己的行掩码。
