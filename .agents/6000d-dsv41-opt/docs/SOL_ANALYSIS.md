## 口径

- SOL 取三个下限里最大的一个：算力（FLOPs ÷ 张量核峰值）、显存带宽（必须从显存读写的字节 ÷ 带宽）、
  跨卡链路（必须传输的字节 ÷ 链路带宽）。
- 达成率 = SOL ÷ 实测。差距 = (实测 − SOL) × 启动次数。
- 峰值和带宽是在 `.29` 的 RTX 6000D 上实测的，不是标称值：

| 项目 | 实测 |
| --- | ---: |
| 显存读带宽 | 1333 GB/s |
| 显存拷贝 | 640 GB/s |
| L2 内数据的读带宽 | 约 3500 GB/s |
| BF16 GEMM（cuBLAS，大形状） | 最好 225 TFLOP/s，持续 140–165；采样里 `wo_a` 实际跑到 320 |
| MXFP8 GEMM（FlashInfer b12x） | 约 416–458 TFLOP/s（三位分析者各自测得） |
| CUDA Graph 回放，每个空内核节点 | 0.94 µs（其中 0.4 µs 是内核时长，0.54 µs 是间隙） |
| 同机两张卡之间拷贝 | 56.5 GB/s |

小结：

- 差距合计约 27 ms，也就是一步的理论下限约 26 ms，现在是它的两倍。

小结：

- 2048 行下稠密 GEMM 已经到 SOL 的八九成，没有空间；试过的替代（DeepGEMM、拆组、换布局）都不更快。
- 差距集中在三处：MegaMoE（负载不均和等网卡）、注意力内核的实现、以及 QCP8 特有的通信和空闲。
- 被实测推翻的早期判断：我曾说 Prefill 的 MoE 卡在“同机也走网卡”上，把传输改成 LSA 后金标准没有变化
  （4.593 对 4.596 req/s）；我当时用的算力上限也高估了约一个数量级。

## 这张卡有一个按 SM 计的算力配额（实测）

三位分析者在不同的卡上各自看到张量核满载几毫秒后突然变慢。专门刻画的结果（`.29` 的 GPU 2 和 GPU 7，
两张卡表现完全一样；原始数据在临时目录的 `sol/stall/`）：

- **它是配额，不是固定占空比。** 每个 SM 有一个固定的 8.32 ms 窗口（各 SM 的相位不同），窗口内的算术量
  按“FLOPs × 操作数位宽”计费，额度是每个 SM 每窗口 1.18e11。用完之后这个 SM 降到 2.6% 的速度，直到窗口结束。
- **持续上限**：整卡的 FLOP/s × 位宽恒定在 2284–2320e12，略低于 2400。换算成各数据类型：

| 数据类型 | 突发峰值 | 持续上限 |
| --- | ---: | ---: |
| BF16 | 340–370 TFLOP/s | 144–145 TFLOP/s |
| FP8，以及 MegaMoE 用的 MXFP8×MXFP4 | 520–739 TFLOP/s | 286–290 TFLOP/s |
| FP4 | 1290–1477 TFLOP/s | 576–578 TFLOP/s |

- **什么计费**：所有张量核运算和标量浮点运算共用一个额度。访存受限的工作和整数逻辑不计费，也不被降速。
- **`nvidia-smi` 上什么都看不到**：P0、没有事件原因、计数器不变、时钟正常。
- **没有绕过的办法**：试过的各种“干一会儿歇一会儿”的节奏，平均吞吐都不超过降速后的平均值。
- 额度恒定在 2400 以下，像是有意设置的限制（这张卡型号里的 D）。原因本身没有查证。

对我们的含义：

- **Decode 不受影响。** 一步的算术量约为一步内总额度的两成，内核又短又分散。
- **Prefill 受影响，而且这解释了 MoE 的“负载不均”。** 一次编码层 MegaMoE 的算术量是一个窗口额度的 38%，
  均匀分布时不会触发。但某张卡的负载超过平均的 2.1–2.6 倍时，它在一个窗口内就会用完额度，只能等下一个窗口，
  其他卡陪着等。内核级实测里“一张卡 3 倍负载时 11.2 ms、4 倍时 14.5 ms”正好是多等一到两个窗口。
  所以按层均衡专家负载是对症的。
- **位宽越低越便宜。** 同样的 FLOPs，BF16 的计费是 FP8 的两倍，TF32 是 BF16 的两倍。Prefill 注意力现在的 PV
  用三遍 TF32，按配额算是最贵的写法。
- **Prefill 的 SOL 多了一个下限。** 一次 forward 的算术量约 3.3e14（FLOPs × 位宽），按整卡额度至少需要约 150 ms，
  而现在 ADP8 一次 forward 是 365 ms。也就是说即使所有内核都理想，ADP8 最多也只能快到约 2.4 倍。
