# 单节点（EP8）对两节点（EP16）：每张卡的吞吐

日期 2026-11-27 到 28。8x RTX 6000D（156 SM，每卡 85.65 GB）的节点一台或两台：一台是 attention DP8、MoE EP8，
两台是 DP16、EP16。两个 MoE 后端都量：`mega_moe`（FlashInfer 的常驻融合 kernel，下面叫常驻 kernel）和
`mega_moe_split`（CuTe DSL 的分离式 kernel，目标模型用它，DSpark 草稿模型留在常驻 kernel 上）。两种布局跑
同一棵代码树、同一份 FlashInfer（`flashinfer/README.md`）、同一个开关集（`d7-same.sh`，split 另加
`d7-same-split-ep16.sh` 的两个设置）。

要回答的问题：每张卡的负载相同，把 8 张卡的 EP 组扩成 16 张卡，每张卡的吞吐是多了还是少了。

原始数据在 `results/ep8-vs-ep16-20261127/`，脚本在 `realtext/`、`launch/`、`placement/`。

## 结论

1. **每张卡的负载相同时，EP16 每张卡的产出比 EP8 高。** 真实文本加各自的静态放置（第 3、4 节）：常驻 kernel
   的每卡吞吐在 1 路时相同（+1% 到 +2%），2 路 +7% 到 +9%，4 到 24 路 +14.3% 到 +21.5%；split 在两边都用 kernel 表、
   都打包时，1 路高 5.4% 到 6.6%，2 到 16 路高 13% 到 22%，24 路高 6.5% 到 9.2%。两台节点合成一个 EP16 组，整机吞吐是一台节点 EP8 的 2.0 到 2.5 倍。
2. **均衡路由下方向相同，幅度更大**（第 2 节，合成 token）：EP16 的一步在每 GPU 1 到 16 路短 12% 到 24%（常驻
   kernel）和 18% 到 30%（split），32 路只短 2% 到 6%。
3. **原因是推断，没有单独量**：小并发时一次 MoE launch 的时间主要花在读专家权重上，每个有流量的专家读一遍。
   EP8 每张卡持有 48 个专家，EP16 每张卡 24 个，每卡请求数相同时 EP16 每张卡读的权重更少。并发升高后算力成为
   瓶颈，差距收窄。
4. **两种布局选后端的规律相同，交叉点不同**（只重排的放置）：EP8 的 split 到每 GPU 8 路领先 7% 到 14%，
   12 和 16 路打平（+0.6% 和 -1.5%），24 路落后 5.2%；加上强制打包后到 8 路领先 8.5% 到 15.1%，12 / 16 路领先
   5.6% / 2.2%，24 路落后 2.3%。EP16 的 split 到 12 路领先 7% 到 21%，16 路打平，24 路落后 6.7%。
5. **放置解对以后，真实文本不需要冗余副本。** 只重排就把最忙的 rank 压到平均的 1.00 倍。再加副本，EP16 的
   split 每档都少 2% 到 3%，EP8 的 split 相差不超过 1%，常驻 kernel 在 -2% 到 +1% 之间，每张卡多占 1.5 到 3.0 GB
   显存。建议只重排。
6. **比较不同 EP 规模或不同放置的 split 之前要核对两件事**（第 5 节）。FlashInfer 按专家槽总数精确匹配
   kernel 表，带副本的放置槽数变了就退回规则选择，日志里不报错：EP8 在每 GPU 24 路因此少 11.9% 的吞吐。
   FlashInfer 的规则只在 EP16 打包分发：EP8 加 `MEGAMOE_XNUMA_PACK=1` 后真实文本在每 GPU 8 路以下多 0.6% 到 1.3%，12 到 24 路多
   3.0% 到 4.9%。
7. **EP8 的 split 引擎显存很紧**：结束时最满的一张卡 83.3 GB（只重排）和 84.7 GB（带副本），卡上共 85.65 GB。
   EP16 的 split 是 78.9 和 82.0 GB。

## 1. 条件

| | 单节点 | 两节点 |
| --- | --- | --- |
| 布局 | DP8、EP8，一个节点 8 个 rank | DP16、EP16，两个节点各 8 个 rank |
| 每卡 N 路时的并发 | 8N | 16N |
| `--max-num-seqs` | 512 | 1024 |
| 其余 `ts serve` 参数、开关集、代码、FlashInfer | 相同 | 相同 |
| 放置文件 | 用 EP8 引擎录的统计求解 | 用 EP16 引擎录的统计求解 |
| split 的 kernel 表 | `ep8_2numa` | `ep16_2x2numa` |
| split 的打包分发（pack） | FlashInfer 的规则：不打包；另量了强制打包的一组 | 打包 |

- 两种布局下每张卡的活一样多：每张卡一个 attention rank，请求数相同；MoE 的总行数随卡数翻倍，每张卡持有的
  专家减半，所以每张卡每步算的专家行数也相同。不同的是每个专家收到的行数翻倍，rank 间传输的对端从 7 个
  变成 15 个，其中 8 个在另一个节点上。
- 真实文本的负载见 `realtext/README.md`：8192 token 的提示词，输出 1024 token，贪心，真实的 DSpark 接受率，
  闭环波次，只量 decode 窗口，每档取前三个分布均匀的有效波次的中位数。两种布局喂同一批提示词：两节点在
  并发 2N 时用提示库的第 0 到 2N-1 条；单节点在并发 N 时量两次，分别用第 0 到 N-1 条和第 N 到 2N-1 条，
  取两次的平均。接受长度取决于提示词，这样两边才对得上（第 3 节的表里两边相差不超过 0.6%）。
- 一步的耗时 = TPOT × 接受长度，是一个请求走一个 decode 周期的时间，不受接受长度差异的影响。
- 放置：两种布局各自用留出提示库（种子 43，和被测的一套没有重复）在自己的 EP 规模上录 decode 负载统计
  （只数真实行，见 `docs/LOAD_PROFILE_FILLER_ROWS.md`），再用
  `solve_placement.py --modes decode --replica-threshold 0.25` 求解。EP16 给 `--replicas 4`，得到每 rank 4 个
  副本槽（共 448 个专家槽）。EP8 给 `--replicas 8`，求解器只用了 3 个（共 408 槽；给 4 也是 3 个）：副本只给
  负载超过平均 rank 负载 25% 的专家，EP8 的平均 rank 负载是 EP16 的两倍，够得上的专家更少。两份放置在各自
  的统计上都把最忙的 rank 压到平均的 1.000 倍，跨 rank 的路由占比 EP16 是 85.7%，EP8 是 84.3%。
- 启动：`launch/realtext-engine.sh dep8` 或 `dep16`。常驻 kernel 用 `OPT_EXTRA_ENV=switch-sets/d7-same.sh`；split 用
  `d7-same-split-ep16.sh` 加 `OPT_MOE_BACKEND=mega_moe_split`（文件名里的 ep16 是它的来历，这里 EP8 的 split 用的
  也是它；其中打包门槛那一项在 EP8 不起作用，见第 5 节）。放置文件在所用的开关文件里用
  `TOKENSPEED_MOE_EXPERT_PLACEMENT` 给出。客户端是 `realtext/bench_closed_wave.py`，单节点加 `--dp 8` 和 `--offset`。

## 2. 均衡路由下的步时（合成 token）

`TOKENSPEED_MOE_ROUTING_SIMULATION=balanced` 让每一行的 top-k 专家均匀轮转（专家照常计算，只换路由），所以
不需要放置。量法是 `launch/README.md` 的步时测量：合成 token，131072 token 的上下文，接受长度模拟为 6，
每个 rank 固定 B 个请求，取两轮各 50 个步间隔、去掉最小和最大各 20 个之后的平均。另起一次带负载统计的
运行，用 `placement/check_balance.py` 确认路由确实均匀（最忙的专家是平均的 1.001 倍）。

一步的耗时（毫秒）：

| 每 GPU 路数 | 1 | 2 | 4 | 8 | 16 | 32 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| EP8 常驻 | 46.90 | 54.27 | 55.67 | 58.49 | 64.76 | 75.59 |
| EP16 常驻 | 41.33 | 41.30 | 42.51 | 46.71 | 55.97 | 71.00 |
| EP16 对 EP8 | -11.9% | -23.9% | -23.6% | -20.1% | -13.6% | -6.1% |
| EP8 split | 40.83 | 48.78 | 49.39 | 52.81 | 61.31 | 76.33 |
| EP16 split | 33.58 | 34.26 | 35.03 | 39.75 | 50.54 | 74.65 |
| EP16 对 EP8 | -17.8% | -29.8% | -29.1% | -24.7% | -17.6% | -2.2% |

- 每一轮单独算（各取中间 30 个步间隔），两轮相差不超过 0.3%。例外是 EP16 split 的 32 路：有几个步间隔特别长
  （最长 141 毫秒），不截尾的话两轮是 77.21 和 75.10 毫秒，所以这一档的 -2.2% 只能算打平。
- 三次 EP8 运行的输入哈希相同，两次 EP16 运行的输入哈希相同。
- 没有副本，两边的 split 都用上了各自的 kernel 表（384 槽）。
- 每卡吞吐与步时成反比：EP16 的常驻 kernel 每卡多 13% / 31% / 31% / 25% / 16% / 6%，split 多 22% / 42% / 41% /
  33% / 21% / 2%。
- 原因（推断，没有单独量）：小并发时一次 MoE launch 的时间主要花在读专家权重上，每个有流量的专家读一遍，
  和它收到几行关系不大。均衡路由下所有专家都有流量：EP8 每张卡持有 48 个专家，EP16 每张卡 24 个，同样的
  每卡请求数下 EP16 每张卡读的权重少一半。EP8 从 1 路到 2 路多出 7 到 8 毫秒（1 路时全组 48 行、288 条路由，
  384 个专家里只有四分之三有流量；2 路起全部都有），EP16 在 1 路时 24 个就已经全有，1 路到 2 路几乎不变。
  并发升高后算力成为瓶颈，这个差距收窄到 32 路的 2% 到 6%。
- 这组数的绝对值不能和别的表混着看：均衡路由是“有流量的专家最多”的极端情况，同一量法下不做放置的合成
  token 路由集中在少数专家上，1 路的步时反而短得多（`docs/EP16_SPLIT_RESULTS.md` 第 5 节）。
- EP8 的 split 不带 6×2^N 行的桶再跑一次：40.91 / 48.77 / 49.42 / 53.48 / 61.30 / 78.94。8 路（48 行）和
  32 路（192 行）受益于专用桶，步时短 1.3% 和 3.3%，其余档相差不超过 0.2%。
- EP8 的 split 默认不打包，EP16 打包。EP8 强制打包再跑一次，步时短 0.4% 到 2.1%（第 5 节），上面的结论不变。

## 5. 比较两种 EP 规模的 split 时要核对的两件事

这两件事都不报错，只能从引擎日志里看出来。这次的 EP8 split 第一次运行两件都没对上。

**kernel 表按专家槽总数精确匹配。** FlashInfer 用（模型形状、专家槽总数、拓扑、设备）找 kernel 表，找不到
就用规则选择。带副本的放置槽数不是 384：EP16 每 rank 4 个副本槽是 448，EP8 每 rank 3 个是 408。求解器的
`--replicas` 是上限，实际槽数由流量决定（第 1 节），所以表要按实际槽数登记。本分支在 EP16 登记了 448 槽，
在 EP8 登记了 408、416 和 448 槽（都是 384 槽那份表的拷贝，没有在这些槽数下重新调优）。

EP8、带副本的放置、真实文本，每张卡每秒输出 token：

| 每 GPU 路数 | 1 | 2 | 4 | 8 | 12 | 16 | 24 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 规则选择（没有匹配的表） | 116.1 | 191.7 | 320.7 | 536.0 | 699.6 | 851.5 | 997.9 |
| kernel 表 | 115.7 | 191.6 | 320.6 | 535.8 | 707.0 | 865.1 | 1132.9 |
| 表对规则 | -0.3% | -0.1% | -0.0% | -0.0% | +1.1% | +1.6% | +13.5% |
| kernel 表，强制打包 | 117.0 | 193.0 | 322.4 | 542.7 | 741.0 | 894.6 | 1178.8 |
| 打包对不打包 | +1.1% | +0.8% | +0.6% | +1.3% | +4.8% | +3.4% | +4.0% |

- 每 GPU 8 路以下有没有表都一样，12 和 16 路用表多 1.1% 和 1.6%，24 路（192 行的桶）多 13.5%
  （反过来说，没有表少 11.9%）。
- 核对办法：引擎日志里每个桶有一行 `[FlashInfer MegaMoE compile] rank=0 ... bucket=192 ...`。EP8 用了表是
  `K1=(64, 64, 128) ... tail_reclaim=True ... green=120/36`，规则选择是 `K1=(64, 32, 128) ...
  tail_reclaim=False ... green=104/52`（EP16 用了表也是
  `tail_reclaim=True ... green=120/36`）。`TOKENSPEED_MOE_EXPERT_PLACEMENT` 那一行日志有放置的槽数。

**打包分发只在 EP16 默认打开。** 打包指跨 NUMA 和跨节点只发送路由到对端的那些行（`flashinfer/README.md`）。
FlashInfer 的规则只给 EP16 定了打包的行数门槛，EP8 不打包；`MEGAMOE_XNUMA_PACK_MIN_TOKENS` 只能在有门槛的
地方移动门槛，对 EP8 没有作用。`MEGAMOE_XNUMA_PACK=1` 在任何 EP 规模下强制打包。引擎日志里 EP8 默认是
`n_cross=4 fsplit=2 pack=False`，EP16 是 `n_cross=12 fsplit=2 pack=True`。

- EP8 强制打包，真实文本（上表后两行）：每 GPU 1 到 8 路多 0.6% 到 1.3%，12 / 16 / 24 路多 4.8% / 3.4% / 4.0%。只重排的
  放置下也一样（第 4 节的表）：多 1.1% / 1.0% / 0.7% / 1.2% / 4.9% / 3.8% / 3.0%。
- EP8 强制打包，均衡路由的步时（第 2 节的量法，1 到 32 路）：40.41 / 48.47 / 49.10 / 52.59 / 60.05 / 75.98
  毫秒，比不打包短 1.0% / 0.6% / 0.6% / 0.4% / 2.1% / 0.5%。
- 所以在这种 2 个 NUMA 的节点上，EP8 的 split 应该加 `MEGAMOE_XNUMA_PACK=1`。它没有改变第 3 节的结论：
  两边都打包，EP16 的 split 每卡仍然高 5.4% 到 19.6%（带副本）和 6.6% 到 22.3%（只重排）。

## 6. 范围和没做的

- 单节点只在节点 0 上量过一个 EP8 组。两台节点各跑一个 EP8 组的整机吞吐按两倍算，没有两组同时跑。
- 一个提示库（ShareGPT，8192 token）、一种输出长度、闭环波次。别的流量路由分布不同，放置要重录重解，
  两个后端的交叉点也会移动。
- 每 GPU 最多 24 路（真实文本引擎的图捕获上限）。
- 只量了 decode。prefill 不在范围内。
- 结论 3 的原因没有用 kernel 级的计时验证。
- EP8 的 408 槽和 EP16 的 448 槽用的是各自 384 槽那份 kernel 表的拷贝，没有重新调优。
- 两个后端的输出在同一精度档但不是逐位相同，split 的接受长度在多数档比常驻 kernel 低 0 到 1.4%（1 路低
  3% 到 4%，只有 8 或 16 个请求），这个差已经算在吞吐里。
